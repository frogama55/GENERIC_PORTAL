# セキュリティ指針（この拡張を安全に保つための考え方）

この拡張の目的は「対象ポータルを使いやすくする」こと。元々は開発者自身の個人利用のみを
想定していたが、現在は**限定公開（Unlisted）** の形で他の利用者にも共有する方針としている。
そのために**守るべきセキュリティ上の性質**と、新機能を足すときの判断基準をまとめる。
新しい機能を検討するときは、必ずこのファイルの「機能追加チェックリスト」を通すこと。

## 守りたいこと（脅威モデル）

1. **認証情報の機密性**：パスワード・セッション・トークンを拡張が読まない／保存しない。
2. **第三者へのデータ流出防止**：個人情報や掲示内容が「ポータル以外の相手」に渡らない。
3. **対象システムに害を与えない**：サーバへ余計な負荷をかけない・データを書き換えない。

## いちばん大事な考え方

### ① 危険なのは「通信すること」ではなく「誰と」通信するか

- ブラウザは元々ポータル(`portal.chibatech.ac.jp`)と通信している。拡張が**同じ相手（same-origin）**へ
  リクエストするのは、ページが元々やっていることの延長にすぎず、情報漏洩には当たらない。
- 漏洩が起きるのは**サードパーティ**（拡張作者のサーバ、分析サービス、外部ビューア、CDN等）へ
  データを送ったとき。
- よって原則は「外部と通信しない」ではなく、正確には次：
  > **ポータル自身以外へはデータを送らない。**

### ② 認証情報は「読まない」構造にする

- same-origin の `fetch` ではクッキーは**ブラウザが自動付与**する。拡張コードが値を読む必要はない。
- ポータルのセッションクッキーは `HttpOnly`（＝JavaScriptから中身を読めない）。仮にコードが
  悪意を持っても読めない。この前提を崩さない（`document.cookie` やトークンを読み書きしない）。

### ③ 「約束」より「構造」で守る（最小権限）

- `manifest.json` の `host_permissions` は**ポータルのみ**に限定する。こうすると、たとえコードに
  バグがあっても他ドメインへは通信できない（権限が無いから送れない）。
- 要求権限は必要最小限（現状は `storage` のみ）。`<all_urls>`・`tabs`・`history`・`cookies` などの
  広い権限は要求しない。
- コードはローカルの素の JS/CSS で短く保ち、いつでも全部読めるようにする（ビルド無し・自作・
  手元管理。ストア配布の自動更新によるサプライチェーンリスクも無い）。

## やってよいこと / だめなこと

| 安全（左側だけで作る） | 危険（やらない） |
|---|---|
| Chrome内蔵ビューア等でローカル表示（blob） | オンラインの外部ビューア/サービスに渡す（＝アップロード＝流出） |
| ポータルへの same-origin fetch | 取得データを分析/自前サーバ/外部へ送信（テレメトリ含む） |
| 権限はポータル限定・`storage`のみ | `<all_urls>`・`cookies`・`history` 等の広い権限要求 |
| クッキーは自動付与（中身は読まない） | `document.cookie`・トークンの読み取り/保存 |
| 人間の操作を起点に発火・読み取り専用 | 自動ポーリング・連続取得・サーバへの書き込み |

## サーバ（対象システム）への配慮

- 機能は**人間の操作を起点**に発火させる（自動ポーリング・ループ取得を入れない＝人間と同じ頻度）。
- 読み取りに徹し、ポータルのデータを書き換えない。
- 利用規程が確認できないため、「**ログイン中の本人が手動でやる操作を少し便利にするだけ**」の
  範囲を超えない。自動化・改変を厳しく制限する規程もあり得るので、人間起点・読み取り専用を維持する。

## 利用者が広がることへの対応（限定公開の判断）

自分1人だけでなく不特定多数（対象ポータルの学生・教職員）が使うようになると、リスクの性質が
変わる。単純な「本人が手でやる操作の代替」から、「多数の利用者が同種の自動化を行う」構図に
見え方が変わりうるため、以下を判断基準にしている。

- **限定公開（Unlisted）に留める**：検索・一覧には出さず、共有されたリンクを知っている人だけが
  インストールできる形にする。無差別な拡散を避け、想定外の規模での利用を防ぐ。
- **書き込みをしない原則は規模が変わっても崩さない**：現状すべての自動操作（成績ページの表示
  切替、掲示の展開、添付取得など）は「表示の絞り込み・取得」であり、フォームの登録・保存など
  データを書き換える操作を利用者の明示的な操作なしに行う機能は一つも実装していない。この一線は
  今後も維持する。新機能追加時は必ずこの点を確認する。
- **利用規程の確認は継続課題**：正式な規程を確認できていない状態での公開判断であることを認識し、
  確認できた場合はその内容に従って機能・公開範囲を見直す。
- **保守できない自動化機能は増やしすぎない**：対象サイトの実装変更で壊れた場合、直せるのは
  開発者本人のみ。壊れ方は表示不具合に留まる設計だが（データ破壊を伴う失敗はしない）、利用者が
  増えるほど影響範囲は広がることを意識する。

## 機能追加チェックリスト（新機能ごとに確認）

- [ ] **何を読むか**：個人情報・認証情報を読んでいないか（クッキー/トークンを読まない）。
- [ ] **どこへ送るか**：通信先はポータル自身(same-origin)だけか。第三者ホストが一切登場しないか。
- [ ] **どこに保存するか**：必要最小限か。機微データを永続化していないか（表示のための一時保持のみ）。
- [ ] **権限**：新たな広い権限を要求していないか。manifest がポータル限定のままか。
- [ ] **起点**：人間の操作起点か。自動・高頻度アクセスになっていないか。
- [ ] **書き込み**：サーバのデータを変更していないか（読み取り専用か）。
- [ ] **失敗時**：壊れず、素の挙動に安全に戻るか。
- [ ] **可読性**：コードは短く読めるか。ON/OFF で無効化できるか。

## 具体例：添付ファイルのブラウザ内プレビュー（attachment.js）

この機能は上記を満たすよう設計している（[[selectors]] / privacy.md も参照）：
- 取得は**ポータルへの same-origin fetch のみ**。第三者へは送らない。
- クッキーは自動付与、値は読まない（HttpOnly）。
- 取得PDFは表示のための**一時的な blob**。保存も外部送信もしない。
- 新たな権限は不要（`host_permissions` はポータルのまま）。
- 人間が「ダウンロード」を押した時だけ発火。失敗時は通常のダウンロードにフォールバック。
